# KNX SD-WAN 维护终端管理方案 V1.1（审阅版）

> **状态：方案存档 / 待审计 / 未实施**  
> 本文记录维护终端管理功能的设计方向和用户已确认的约束，不代表功能已经开发、部署或通过现场验收。

## 1. 目标

在现有 KNX SD-WAN V1.0 基础上，为手机、笔记本及未来的维护设备提供统一的接入管理能力。

预期目标：

- 维护终端通过 WireGuard 安全连接家庭网络。
- 连接后访问现有 R86S LuCI「KNX 客户维护」页面。
- 维护终端默认仅访问获准的家庭 LAN 资源，例如家庭 NAS、路由器管理页面。
- 客户业务仍由现有 KNX SD-WAN ON/OFF 机制控制。
- 未来新增或撤销维护设备可通过管理界面完成，不必每次手工修改路由器配置。

本阶段优先复用现有 LuCI 页面、控制器和 WireGuard 基础设施，不立即开发一套全新的管理平台，也不开放公网 Web 管理端口。

## 2. 已确认的设计决策

### 2.1 WireGuard 架构先审计，再决定

暂不预先决定维护终端应加入个人 WG、客户业务 WG，还是新建独立维护 WG。

先对现有源码、配置和策略路由进行只读审计，比较方案的复杂度、权限隔离和长期维护成本，再提交架构建议。

### 2.2 设备管理权限仅属于管理员

只有管理员可以：

- 添加维护设备；
- 设置设备名称、所属人员和备注；
- 为设备分配唯一的隧道地址；
- 生成和交付设备配置；
- 查看设备连接状态；
- 禁用、撤销或删除设备；
- 查看设备管理操作记录。

普通工程师及维护终端不能自行创建 Peer，也不能修改其他设备的权限。

### 2.3 维护终端默认仅访问家庭 LAN

- 可以访问获准的家庭 NAS、路由器及其他家庭服务。
- 不直接获得客户真实 LAN 的路由权限。
- 不绕过现有客户业务授权、ON/OFF 状态机、AllowedIPs、路由和防火墙保护。
- 如果未来需要维护终端在业务 ON 时访问客户设备，必须经过现有业务控制机制授权；OFF 时必须阻断客户业务访问。
- 客户 Cudy 继续使用现有客户隧道身份，不与手机、笔记本共用密钥。

访问家庭管理页面不等于获得客户业务访问权限。

## 3. 第一阶段：只读审计

本阶段不创建新 Peer、不修改配置、不重载防火墙、不切换客户业务状态。

### 3.1 WireGuard 与路由审计

检查：

- 个人 WG、客户 WG 的接口、地址规划和防火墙区域；
- 现有 Peer 的登记、生成、更新和撤销方式；
- AllowedIPs 的分配与冲突检测；
- 新增维护 Peer 是否会影响现有客户 Peer；
- 客户业务 ON/OFF 是否可能误删或修改维护终端权限；
- 现有路由和策略规则能否让维护终端安全访问家庭 LAN。

审计输出不得包含私钥、PSK、Wi-Fi 密码或真实认证凭据。

### 3.2 LuCI 与权限审计

检查：

- 「KNX 客户维护」页面的入口和调用流程；
- 现有登录认证与 ACL 权限；
- 后端 RPC 调用 `knx-customer` 控制器的方式；
- 是否可在现有菜单下增加「维护终端管理」；
- 如何限制新功能只管理维护 Peer，避免任意 Shell 命令执行；
- 如何防止重复提交、地址冲突、未授权撤销和并发修改。

### 3.3 比较三种候选架构

| 方案 | 说明 | 重点审计内容 |
|---|---|---|
| 复用个人 WG | 维护设备通过现有个人隧道回家 | 能否作为通用项目方案，权限是否足够隔离 |
| 直接加入客户业务 WG | 在现有客户 WG 中增加维护 Peer | 是否与客户业务开关、客户隔离和 AllowedIPs 生命周期冲突 |
| 新建独立维护 WG | 维护终端与客户隧道分离 | 是否值得增加接口、地址规划、路由和防火墙复杂度 |

Codex 应根据实际源码和规则给出推荐，不得在审计前直接选定某一方案。

### 3.4 第一阶段交付物

1. 现有 WG、路由和权限关系图；
2. 维护 Peer 生命周期代码审计报告；
3. 三种架构的优缺点及复杂度比较；
4. 推荐方案及依据；
5. 需要修改的文件清单和潜在回归风险；
6. 后续开发与验收计划。

## 4. 第二阶段：独立副本开发

第一阶段经审阅后，才在独立开发副本实现维护终端管理。

计划功能：

- 添加设备；
- 设置设备名称、所属人员及备注；
- 自动分配唯一地址；
- 生成配置文件或二维码；
- 查看最近握手和在线状态；
- 撤销设备；
- 查看操作历史。

设备配置交付时，只向管理员展示必要的私钥或完整客户端配置；不得在日志中保存客户端私钥。

初期优先复用现有 LuCI 登录认证，不立即建立独立的网站账号体系。

## 5. 第三阶段：验收要求

部署前至少验证：

1. 新增手机和笔记本不会影响现有客户 WG；
2. 重复添加、地址冲突和非法输入会被安全拒绝；
3. 撤销单个设备不会影响其他设备；
4. 维护设备可以访问获准的家庭 LAN 资源；
5. 维护设备不能绕过业务开关访问客户真实 LAN；
6. 业务 OFF 时客户业务访问被阻断，必要的管理连接仍可用；
7. 业务 ON 时，仍由现有授权规则决定访问范围；
8. 路由器重启、服务重载和配置恢复后，权限仍符合预期；
9. 设备管理页面不能执行任意系统命令，也不能读取其他设备的私钥；
10. 所有变更都有备份、回滚方案和验收记录。

## 6. 生产部署原则

- 生产 R86S、Cudy 保持现状，直至独立副本开发和验收完成。
- 不为开发新功能而重构已验收的 V1.0 核心业务控制器。
- 不新增公网 Web 管理端口。
- 不改变现有客户业务状态。
- 不在未审计前决定维护终端必须加入哪一个 WG。
- 生产变更前先备份、审查差异并准备独立回滚。
- 先添加自己的测试笔记本，再添加手机，最后才考虑其他工程师设备。

## 7. 预期结果

维护终端管理成为 KNX SD-WAN 的一项通用能力。管理员可以在现有网页添加或撤销手机、笔记本及未来的工程师终端；维护终端访问家庭 LAN 的权限与客户业务授权分开管理，现有客户 ON/OFF 机制继续承担业务访问控制。

## 8. 当前下一步

**只读审计现有架构，提交推荐方案，等待管理员审阅后再开始独立副本开发。**

本文仅为规划记录，不是部署说明，不授权任何生产配置变更，也不表示维护终端管理功能已经实现。
