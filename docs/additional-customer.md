# 第二客户：增量登记与设备兼容

此文记录已完成的 JCG Q30 PRO / OpenWrt 24.10-SNAPSHOT 网关部署经验。所有地址均为虚构示例，没有生产配置、设备公钥或运行日志。不是一键安装程序。

## 独立身份，不复制站点

示例：维护网络使用 10.60.0.0/24，服务端隧道地址为 10.62.0.1。站点 A 使用 10.62.0.11 和维护 LAN 10.61.1.0/24；新增 B 使用 10.62.0.12 和维护 LAN 10.63.1.0/24。实际部署必须先检查冲突，不照抄示例。

1. 每台网关在设备内生成新的 WG 私钥，控制器只接收其公钥。禁止复制 A 的私钥、Wi-Fi 密码、SSH 主机身份或整份配置。
2. 保留现有 WG 接口；增量创建 B Peer，持久与运行 AllowedIPs 初始只含 B 管理 /32，并添加明确的管理 /32 路由。不能重建公共接口或覆盖个人 WG。
3. 在控制器 `clients.json` 与 LuCI `ui-clients.json` 增量增加 B；保留所有 A 数据和显示资料。例如控制器新增项：

```json
"b": {
  "id": "b",
  "peer": "knx_customer_b",
  "tunnel": "10.62.0.12",
  "lan": "10.63.1.0/24"
}
```

4. 持久状态 `b-state` 初始为 `off`。登记表中的 WG 地址与维护 LAN 不可重叠；当前核心保留全局单业务归属。
5. 管理 guard 与 fw4 精确列举 A、B 管理 /32 的 SSH/HTTP/ICMP 例外，不开放整个隧道区。对应的维护 LAN → 家庭 fw4 规则仍必须依赖早期 guard 和租约；扩大 UCI 正向规则前先验证 guard 已编译生效。
6. `knx_direct_known` 加入新维护 LAN，真实 WAN 子网只由 Agent 确认后登记。业务 OFF 必须阻止错误流量落普通默认出口。
7. 仿照现有维护 LAN → 家庭的主表旁路策略，为 B 选择未占用的独立优先级；实机使用了 1703，但其他设备必须检查冲突。来源必须为 B 维护 LAN、目标为家庭 LAN，不能添加任意来源的全局旁路。ON 时家庭 → 当前客户的业务策略仍属于控制器表 191。

**现有渲染器一次生成一套基础站点模板，不是多客户合并器。** 不得把为 B 生成的 R86S rootfs 整体覆盖现有 A 配置，也不能原样复制模板中默认 ID a 的登记文件。本轮生产控制器和 LuCI 核心没有被重写。

`integration/r86s/additional-customer.uci.in` 是与本轮变更对应的脱敏 UCI 增量参考，分段用于 network/firewall，不能整份作为单个配置导入。它不修改既有接口，也不自动扩展 guard 或登记表；这些准备未完成前不得启用其中正向业务规则。

## 网关侧适配

- JCG 实机的物理 WAN 设备名是 `wan`，不能照搬另一型号的 `eth0`。Agent 同时核实 ubus、物理链路、DHCP 证据、网关与直连路由；WWAN 仍只作为互联网备用。
- 新增可选参数 `client_listen_port`，省略时默认为 51831。固定本地端口后，增量规则只接收来源 UDP 服务端端口、目标本地 WG 端口的传输报文；仍须通过 WG 密钥认证，不涉及 WAN SSH/Web 放行。
- 同网部署时，主路由既有 LAN 伪装可能让 WG 回包源地址不同于公网 Endpoint。抓包先证明请求/响应，再处理客户端接收规则；不能为解决握手关闭防火墙或改家庭既有 NAT。该规则不保证任意非标准中间 NAT 都可用。
- Dropbear 可能仅监听 WAN。先验证公钥认证与主机指纹，再按 `integration/cudy/dropbear.uci.in` 增加 WG/LAN 的仅公钥实例，保留原管理路径。确认目标固件支持实例和接口绑定。
- fw4 的 script include 由 Shell 执行。使用新增的 `/usr/sbin/knx-direct-reset` 包装器，不能直接把 Lua Agent 当 Shell 文件。
- 新增 prerouting -190 guard，在 OFF 时先于常见代理规则拒绝私有维护 LAN → 家庭，并把来源绑定到实际私有 LAN 接口。不能将来自客户物理 WAN 的伪造维护地址作为可信源。
- WAN 区 input/forward 收紧为 REJECT 前保留当前 SSH 管理例外，并验证独立回滚。关闭不必要 UPnP/NAT-PMP，保留正常 LAN→WAN 上网转发及 masquerade。
- Endpoint 使用已有独立、证书校验的 DoH 刷新；合并域名到固件实际支持的持久 fake-ip-filter，不覆盖已有域名。没有必要为测试启动原本未运行的 OpenClash。
- 新设备若未配置 WWAN，程序支持备用接口不等于已经配置手机热点，更不等于主备断线测试通过。

## 软件包、换行和回滚

定制源失效时，不直接改源或强装内核包。本轮缺少 conntrack：使用官方同发行系列、同架构用户态包，先以现有信任密钥验证索引签名，再校验每个包的 SHA256 和依赖兼容性。工具不全时可在另一台已信任的本地设备验证签名；不得跳过验证、关闭 TLS 校验或从任意镜像混装。

部署所有 Shell、Lua、nft 文件前保证 LF；本轮本地编辑过的 nft 文件因 CRLF 未通过检查，已在恢复原配置后修正。渲染器统一输出 LF，后续编辑/上传也必须保留；检查通过之前不应用规则。

定制 fw4 可能实际加载成功后因最后的可选文件测试返回 1。本轮已查明这个具体固件行为，并核对实际 guard、日志及 Agent reset；**不能推广为“忽略 fw4 非零退出”**，也没有在发布版提供通用吞错机制。无法明确证明加载结果时，应回滚停止。

在两端 root-only 目录备份本轮拥有的文件；验证独立于原 SSH 会话的恢复探针，再建立 3–5 分钟保护。回滚只撤销本轮 Peer、路由、登记和文件。验收完成后解除保护；保存最终文件摘要，后续文件发生改变时拒绝盲目整份覆盖。

## 使用边界

控制命令为 `knx-customer b on|off|disconnect|reconnect|status`。当前框架任何业务状态变更会先关闭全局业务归属，不能承诺 B 的 off 操作不影响正在 ON 的 A。

当 B 的 WAN 仍接维护家庭网段，ON 应拒绝，而不是暂时绕过冲突检查。进入独立客户网络后再验收实际 DHCP 候选、ON/OFF 双向流量、SNAT、已有会话撤销与两客户切换。不要把管理握手或 Linux 规则检查当成这些测试已通过。
